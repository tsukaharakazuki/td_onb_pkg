# TD全体管理者向け おすすめ検知パターン

TD の全体管理者（Admin）が「個別ユーザーが不正を行っていないか（内部不正）」
「アカウントが不正アクセスを受けていないか（外部からの侵害）」を見張るための定番パターンです。
ヒアリングでは **A（外部からの侵害）→ B（内部不正）→ C（運用・棚卸し）** の順に紹介し、
最後に「セット」（§4）から選んでもらうと決めやすくなります。

各パターンは、このWFのルール（`config/` のキー）で実装済みです。

---

## A. 外部からの不正アクセス（アカウント乗っ取り・認証情報の漏洩）

### A1. 許可外の場所からの操作 ★必須
- **狙い**: 漏れたAPIキー・パスワードが社外から使われていないか
- **シグナル**: IPホワイトリスト外のIPから成功した操作（ログイン失敗のみなら「ブロック済み」として重要度を下げる）
- **実装**: 緊急 `emergency_rules.non_whitelist_ip` + `config/ip_whitelist.yml`
- **前提**: オフィス・VPN・連携サーバーのIPを洗い出してもらう。**ここが空だと動作しない**
- **検知時の初動**: 該当ユーザーのAPIキーを無効化 → パスワード変更 → セッション無効化 → 操作内容（ダウンロード有無）を確認

### A2. ログイン失敗の連続 → 成功（総当たりの成功）
- **狙い**: パスワード総当たり・使い回しパスワードによる侵入
- **シグナル**: 同じユーザー×IPで失敗5回以上の後、60分以内に成功
- **実装**: 企業別 `custom_checks.brute_force_success`（daily） / 失敗だけの把握は 日次 `caution_rules.sign_in_failure`
- **検知時の初動**: 本人に確認。心当たりがなければパスワード変更とSSO/MFAの強制

### A3. 休眠アカウントの突然の利用 ★必須
- **狙い**: 退職者・異動者・放置されたアカウントのキーが悪用されていないか
- **シグナル**: 30日以上アクセスがないユーザーが、ログインせずに（＝APIで）クエリ・ダウンロード・キー操作・権限変更
- **実装**: 緊急 `emergency_rules.dormant_user`（`dormant_days`, `sensitive_events`）
- **前提**: `setup_tables.dig` で履歴を初期投入しておく
- **誤検知**: 長期休暇明けの人。その場合は本人確認で解消

### A4. AI・自動化ツールによる探索・接続テスト ★推奨
- **狙い**: 漏れたキーを使ってAIエージェントやスクリプトがデータの在処を探っていないか
- **シグナル**: `SELECT 1` / `SHOW TABLES` / `information_schema` などの探索クエリ、1分あたりのイベント急増、多数のDBへの横断クエリ、権限エラーの繰り返し
- **実装**: 緊急 `emergency_rules.ai_probe`
- **誤検知**: BIツール（死活確認の `SELECT 1`）、社内で認めたAIツール（tdx・MCP）→ `exclude_users` に追加、または `probe_query_min` を上げる

### A5. APIキー発行直後の、普段と違う場所からの利用
- **狙い**: 発行したキーがすぐに第三者に渡っていないか
- **シグナル**: `user_apikey_generate/download` の後24時間以内に、過去30日使っていないネットワーク（/24）から操作
- **実装**: 企業別 `custom_checks.apikey_then_new_ip`（daily）
- **検知時の初動**: キーの用途を本人に確認し、不明なら即無効化

### A6. 短時間に多数のネットワークからのアクセス
- **狙い**: アカウントの共有、キーの拡散（複数の場所で同時に使われている）
- **シグナル**: 1時間に4つ以上の異なるネットワーク（/16）から操作
- **実装**: 企業別 `custom_checks.multi_ip_user`（daily）
- **誤検知**: クラウド上のETL（送信元IPが変わる）→ `exclude_users` に追加

### A7. 制限・監視の解除
- **狙い**: 侵入者が足場を固めるために制限を緩めていないか
- **シグナル**: IPホワイトリスト・パスワードポリシー・SSO設定の変更
- **実装**: 日次 `caution_rules.security_setting_change`（緊急にしたい場合は `severity: critical` に）

## B. 内部不正（個別ユーザーによる持ち出し・権限の悪用）

### B1. 大量のダウンロード・Export ★必須
- **狙い**: 顧客データの持ち出し
- **シグナル**: `job_result_download` の回数・データ量、`job_result_export` の回数
- **実装**: 日次 `caution_rules.data_download` / `data_export`、企業別 `custom_checks.top_downloaders`（週次ランキング）
- **ポイント**: `bytesize` は圧縮後サイズなので、しきい値は MB 単位で小さめに

### B2. 権限付与の直後のデータアクセス
- **狙い**: 権限を自分で（または共謀して）付与して、見られなかったデータを取得する
- **シグナル**: `permission_policy_attach_user` 等の後24時間以内に、付与された人がクエリ・DLを20回以上。自分で自分に付与した場合は強調
- **実装**: 企業別 `custom_checks.privilege_then_access`（daily） / 権限変更自体は 日次 `caution_rules.permission_change`

### B3. 新しい持ち出し先の作成とデータ出力
- **狙い**: 個人のクラウドストレージ等への接続を作ってデータを送る
- **シグナル**: 同じ日に `connection_create` と `job_result_export` / `syndication_run` / ダウンロード
- **実装**: 企業別 `custom_checks.new_connection_export`（daily） / 接続の変更は 日次 `caution_rules.connection_change`

### B4. ワークフローからの社外へのメール送信
- **狙い**: ワークフローの `mail>` でクエリ結果を社外アドレスへ送る
- **シグナル**: `workflow_email_send` の宛先に自社ドメイン以外が含まれる
- **実装**: 企業別 `custom_checks.external_mail_send`（`internal_domains` に自社ドメインを設定して有効化）

### B5. 権限のないデータを探る
- **狙い**: 見てはいけないデータの在処を探す
- **シグナル**: `unauthorized` / `permission_unauthorized_access` / `job_result_download_denied` の繰り返し
- **実装**: 日次 `caution_rules.permission_denied`、緊急 `ai_probe` の権限エラーシグナル

### B6. 業務時間外の重要操作
- **狙い**: 人目のない時間帯の持ち出し
- **シグナル**: JST の業務時間外・土日のダウンロード・Export・キー発行・権限変更
- **実装**: 日次 `caution_special.off_hours_activity`（業務時間を会社に合わせる）

### B7. 重要データ（個人情報DB等）へのアクセス
- **狙い**: 個人情報・売上など重要DBへの、想定外の人のアクセス
- **シグナル**: 指定DBへのクエリ・プレビュー・ダウンロード
- **実装**: 企業別 `custom_checks.watched_table_access`（`watched_databases` を設定）

### B8. 要注意ユーザーの監視
- **狙い**: 退職予定者・委託先・一時アカウントの操作をすべて把握
- **実装**: 企業別 `custom_checks.watch_list_users`（`users` を設定して有効化）
- **ポイント**: 退職予定者は「退職日の1か月前から」が持ち出しの多い時期

### B9. 証跡の確認・隠蔽
- **狙い**: 監査ログのダウンロード（自分の痕跡の確認）、手動でのテーブル削除、監視ワークフローの停止
- **実装**: 日次 `caution_rules.audit_log_download` / `data_deletion` / `workflow_secret_change`
- **追加の推奨**: このWF自体のスケジュール停止（`workflow_schedule_disable`）も `caution_rules` に追加するとよい

## C. 運用・棚卸し

| パターン | 実装 | 頻度 |
|---|---|---|
| 長期間ログインしていないアカウントの棚卸し | 企業別 `custom_checks.inactive_users` | 月次 |
| ユーザーの追加・削除の確認 | 日次 `caution_rules.user_management` | 日次 |
| APIキー操作の確認 | 日次 `caution_rules.apikey_operation` | 日次 |
| 普段と違うIPからのアクセス | 日次 `caution_special.new_ip_for_user` | 日次 |

## 4. 提案セット（ヒアリングの最後に選んでもらう）

| セット | 向いている会社 | 有効にするもの |
|---|---|---|
| **ミニマム** | まず始めたい／通知を増やしたくない | A1, A3, B1（緊急2ルール + 日次のダウンロード） |
| **スタンダード** ★おすすめ | 多くの会社 | ミニマム + A4, A7, B2, B3, B5, C一式（緊急3ルール + 日次レポート + 企業別daily） |
| **ハイセキュリティ** | 個人情報を多く扱う／監査対応が必要 | 全パターン。B4・B7・B8 を設定して有効化し、A7 を緊急扱い（`severity: critical`）にする |

セットを選んでもらった後、§3 の確認クエリと各ルールの試算（SKILL.md Step 5）で
**「1日あたり何件くらい通知が来るか」** を示し、多すぎるルールはしきい値や除外ユーザーで調整します。

## 5. 説明のコツ

- 「どのイベントを使うか」より先に **「何を防ぎたいか」** を聞く（顧客データの持ち出し？乗っ取り？退職者？）
- `ip_address = 'internal'` は TD 内部の自動処理で、人の操作ではないことを必ず説明する（誤解されやすい）
- 検知は「不正の確定」ではなく **「確認すべき兆候」**。通知を受けた後の初動（キー無効化・本人確認）もセットで伝える
- 通知が多すぎると見なくなるため、最初は **スタンダード** で始めて、2週間ほど運用してからしきい値を調整するよう勧める
